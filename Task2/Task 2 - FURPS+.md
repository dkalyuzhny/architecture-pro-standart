| F-09  | Сайт должен принимать кредитную заявку с Ф. И. О. и телефоном. При заполнении паспортных данных должна инициироваться предварительная оценка через систему скоринга с использованием данных БКИ для нового клиента. | Срок получения предварительного решения необходимо уточнить. Ошибка внешней системы не должна трактоваться как кредитный отказ.                                  |
| F-10  | После подачи кредитной заявки на сайте клиент должен получать СМС о дальнейших действиях и необходимости посещения отделения для идентификации и получения кредита.                                                 | Содержание сообщения должно соответствовать результату рассмотрения заявки.                                                                                      |
| F-11  | Сотрудник отделения должен иметь возможность через АБС найти и продолжить заявку, ранее поданную онлайн. При отсутствии заявки должна создаваться новая.                                                            | Необходимы сквозная идентификация заявки и согласование её состояния между системами.                                                                            |
| F-12  | Интернет-банк должен показывать персональные предодобренные кредитные предложения и принимать кредитную заявку с указанием счёта зачисления и необходимых данных. Подача должна подтверждаться СМС-кодом.           | Предодобренное предложение должно быть связано с клиентом и созданной заявкой.                                                                                   |
| F-13  | При подаче заявки по предодобренному предложению должна проверяться необходимость повторного скоринга. При изменении ситуации должна выполняться упрощённая повторная оценка.                                       | Требуется определить признаки изменения ситуации, срок действия предложения и состав упрощённой проверки.                                                        |
| F-14  | Клиент должен получать СМС об изменениях статуса кредитной заявки.                                                                                                                                                  | Перечень статусов, требующих уведомления клиента, необходимо согласовать.                                                                                        |
| F-15  | Передача чувствительных данных сайта и интернет-банка должна выполняться по соединениям с шифрованием трафика.                                                                                                      | Защита должна охватывать и межсистемные соединения, передающие чувствительные данные.                                                                            |
| F-16  | Доступ к заявкам, паспортным данным, персональным предложениям и изменению ставок должен разграничиваться по ролям и принадлежности данных клиенту.                                                                 | Предотвращает просмотр чужих данных и несанкционированное изменение условий при работе нескольких каналов и подразделений.                                       |
| F-17  | СМС-код должен быть одноразовым, ограниченным по времени и числу попыток и связанным с конкретной операцией и её существенными параметрами.                                                                         | Предотвращает повторное использование кода и подтверждение операции с подменёнными параметрами. Значения ограничений требуют согласования.                       |
| F-18  | Должна сохраняться история изменения ставок, условий, решений и статусов с указанием автора и времени, а также сведения о подтверждении операции клиентом.                                                          | Необходимо для аудита и разбора спорных ситуаций. СМС-коды и избыточные персональные данные не должны попадать в журналы.                                        |
| F-19  | Должны фиксироваться необходимые согласия на обработку персональных данных и запросы в БКИ; должны быть определены сроки хранения и удаления данных.                                                                | Влияет на формы, модель данных и интеграции. Состав согласий и сроки согласуются с ответственными подразделениями банка.                                         |
| U     | **Удобство использования (Usability)**                                                                                                                                                                              |                                                                                                                                                                  |
| U-01  | Новые интерфейсы должны соответствовать принятой в банке дизайн-системе, включая цвета, компоненты и брендированные элементы.                                                                                       | Влияет на выбор интерфейсных компонентов и их повторное использование.                                                                                           |
| U-02  | После отправки заявки клиент должен видеть результат её приёма, номер и следующий шаг. Длительная обработка должна отображаться отдельным статусом.                                                                 | Ручное рассмотрение и внешние проверки требуют отделить подтверждение приёма от завершения обработки.                                                            |
| U-03  | При ошибке или повторной отправке клиент должен понимать, принята ли заявка. Должна быть предусмотрена возможность безопасного продолжения заполнения.                                                              | Снижает количество повторных заявок при сбоях связи. Способ сохранения введённых данных должен учитывать их чувствительность.                                    |
| R     | **Надёжность (Reliability)**                                                                                                                                                                                        |                                                                                                                                                                  |
| R-01  | Клиентские сервисы должны работать круглосуточно с доступностью не ниже 99,9%.                                                                                                                                      | Требуется согласовать период измерения, состав операций и учёт плановых работ. Для периода в 30 дней бюджет недоступности составляет около 43 минут.             |
| R-02  | При отказе основного ЦОД сервисы интернет-банка должны сохранять доступность в пределах согласованного SLA. Резервный ЦОД должен выдерживать требуемую нагрузку.                                                    | Текущая работа на одной группе серверов в одном ЦОД требует изменений. Наличие резервного ЦОД без проверенного переключения недостаточно.                        |
| R-03  | Должны быть определены допустимое время восстановления — RTO — и допустимая потеря данных — RPO. Должны проверяться восстановление и переключение на резервную площадку.                                            | Доступность 99,9% не определяет допустимую потерю данных и длительность отдельного восстановления. Числовые значения требуют согласования.                       |
| R-04  | Заявка, приём которой подтверждён клиенту, должна сохраняться при сбоях и передаваться на дальнейшую обработку после восстановления зависимых систем.                                                               | Исключает потерю принятых заявок при асинхронной обработке и недоступности АБС или Кредитного конвейера.                                                         |
| R-05  | Повторные запросы и повторная доставка сообщений не должны приводить к дублированию заявок, открытию нескольких депозитов или повторной выдаче кредита.                                                             | Необходимы идемпотентность операций и контроль уникальности бизнес-действий.                                                                                     |
| R-06  | Для взаимодействий с АБС, скорингом, БКИ и СМС-шлюзом должны быть предусмотрены ограниченные таймауты, управляемые повторы и восстановление незавершённой обработки.                                                | Предотвращает каскадные отказы и дополнительную нагрузку на недоступные системы.                                                                                 |
| R-07  | Должны выявляться расхождения статусов, потерянные сообщения и заявки, длительно не переходящие на следующий этап. Должен существовать способ восстановления обработки.                                             | Доступность отдельных систем не гарантирует завершения сквозного бизнес-процесса.                                                                                |
| R-08  | Ошибка отправки СМС-уведомления не должна отменять успешно завершённую бизнес-операцию; отправка должна восстанавливаться отдельно.                                                                                 | Следует различать информационное СМС и СМС-подтверждение, без которого операция не может быть выполнена.                                                         |
| P     | **Производительность (Performance)**                                                                                                                                                                                |                                                                                                                                                                  |

| P-02  | Заявки по предодобренным кредитным предложениям должны обрабатываться сотрудниками в течение того же рабочего дня.                                                                                                  | Требуется определить время отсечения, рабочий календарь и результат обработки: решение сотрудника либо выдача средств. Суточный обмен не гарантирует выполнение. |
| P-03  | Новые онлайн-процессы не должны превышать согласованные лимиты нагрузки на АБС и её базу данных.                                                                                                                    | База АБС уже перегружена. Требуется определить допустимую интенсивность обращений и конкурентной обработки.                                                      |
| P-04  | Дополнительные процессы предварительного расчёта кредитных предложений не должны увеличивать нагрузку на скоринг в рабочие часы.                                                                                    | Фоновые предрасчёты необходимо отделить от оценки реально поданных заявок. Расписание и ресурсы требуют согласования.                                            |
| P-05  | Новые масштабируемые компоненты должны поддерживать горизонтальное увеличение мощности и распределение запросов между экземплярами. Распределение между ЦОД должно соответствовать выбранной схеме резервирования.  | Не означает обязательную работу всех систем в режиме active-active. Ограничения АБС учитываются отдельно.                                                        |
| P-06  | Должны быть определены средняя и пиковая нагрузка, количество одновременных пользователей, объёмы заявок и запас мощности при отказе площадки.                                                                      | Без профиля нагрузки невозможно проверить быстродействие и достаточность ресурсов резервного ЦОД.                                                                |
| P-07  | Для ставок, кредитных условий и предодобренных предложений должна быть установлена допустимая давность данных. При подаче заявки должна проверяться применимость условий.                                           | Позволяет снижать нагрузку за счёт кэширования без неконтролируемого использования устаревших предложений.                                                       |
| S     | **Поддерживаемость (Supportability)**                                                                                                                                                                               |                                                                                                                                                                  |
| S-01  | Должна быть подготовлена документация по архитектуре, интерфейсам, данным, развёртыванию и эксплуатации с учётом дальнейшего расширения системы.                                                                    | Особенно важны контракты интеграций, модель состояний заявки и правила владения данными.                                                                         |
| S-02  | При выборе технологий должны учитываться совместимость с существующими платформами разработки и компетенции сотрудников банка.                                                                                      | Помимо знания языков программирования необходима возможность сопровождать выбранные технологии в эксплуатации.                                                   |
| S-03  | Должен быть организован мониторинг доступности, времени ответа, ошибок, задержек обработки, возраста очередей, отправки СМС и незавершённых заявок.                                                                 | Необходим для проверки SLA и выявления нарушений процесса. | S-04  | Интерфейсы и события интеграций должны версионироваться и поддерживать согласованное обновление взаимодействующих систем.                                                                                           | Системы разных команд и подрядчика могут обновляться независимо.                                                                                                 |
| S-05  | Для ставок должны храниться версии, периоды действия и история согласования.
